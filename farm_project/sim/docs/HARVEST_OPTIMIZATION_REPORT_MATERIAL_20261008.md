## 1. 보고서 작성 시 지켜야 할 해석

1. **현재 주병목은 GPU 관절계 솔버 실행이다.** CPU에서 호출한 `fetch_results`의 벽시계 경과 시간을 CPU의 직접 계산 시간으로 해석하지 않는다.
2. 초기 CPU PhysX 시험과 이후 학습 조건 정렬 후 GPU PhysX 시험은 다른 환경이다. 초기8.30FPS와 후속4.28FPS를 같은 조건의 단순 성능 퇴행으로 비교하지 않는다.
3. 다른 로봇을 정적으로 전환해 얻은7.01FPS는 철회한 조건이다. 최종 목표의 최적화 성과로 사용하지 않는다.
4. 실행 종료코드0, 작업 `SUCCESS`, 실제 과실 적재 성공은 서로 다르다. 후속 Hz/CPU·GPU 성능 비교의 실제 적재는 모두0이다.
5. 설정480Hz는 시뮬 시간의 적분 간격이다. 실제 벽시계 초당480회 계산하거나 화면60FPS를 보장하지 않는다.
6. 사용자 기억의 이전 Nav2 약70FPS는 정확한 당시 조건을 재현하지 못했다. 원본 맵 대조 시험의 실제 FPS는60 제한에서59.56이었다.
7. 실측·코드에서 예상한 값·미검증을 구분한다. 특히 학습 전체 장면의 solver 반복 횟수는 이번에 CUDA 추적하지 않았다.
8. `sim/runs/`의 원본 로그는 Git 제외 대상이다. 이 문서와 함께 저장한 [핵심 증거 요약 JSON](changes/HARVEST_OPTIMIZATION_EVIDENCE_20261008.json)은 원격에서도 읽을 수 있다. 로컬 원본 경로만으로 원격 ChatGPT가 로그 전체를 읽었다고 간주하지 않는다.

## 2. 목표와 지켜야 할 조건

최종 환경은 예찰로봇·수확로봇·운송로봇·선별로봇팔 네 대가 동시에 동작하는 농장이다. 현재 시험 장면의3개 관절계가 모두 동적으로 유지되는 것과 최종 네 대의 동시 미션 완성은 다르다.

수확팔은 전달 Teacher 환경의480Hz 물리·20Hz 정책과 충돌/질량/관성/접촉 조건을 가능한 한 맞춰야 한다. 속도를 위해 다른 로봇을 정적으로 바꾸거나 성공 판정·안전 임계값을 완화하면 안 된다. 시각적 운반과 엔진 내부 위치도 일치해야 한다.

물리·정책·화면의 시간 관계:

| 항목 | 현재 기본값 | 의미 |
|---|---:|---|
| 대기 물리 |60Hz| 한 화면 갱신에 물리1tick |
| 수확 물리 |480Hz| 한 화면 갱신에 물리8tick, 매tick 외력·접촉 처리 |
| 화면 갱신 목표 |60Hz(시뮬 시간)| 실제 벽시계 FPS와 다름 |
| Teacher 정책 |20Hz(시뮬 시간)|480Hz에서는 정책1회당 물리24tick |

예를 들어 이 루프가 현실에서10FPS로 실행되면 한 벽시계 초에 약10/60=1/6시뮬초가 진행한다. 물리tick을 누락해 시간을 따라잡는 방식이 아니다. 전체 PhysicsScene의 주기가 바뀌므로 수확로봇만480Hz, 같은 장면의 다른 로봇은60Hz로 독립 적분하는 구조가 아니다.

측정 PC는 i7-13700K, RTX4070SUPER, Isaac Sim5.1, PhysX107.3 계열이다. 최근 통제 비교는1280×720, 같은 카메라, 카메라/LiDAR 센서OFF, 새 프로세스별 실행이다. 일반 운영 센서·Nav2·네 로봇 동시 부하는 이보다 추가된다.

## 3. 작업 경과

### 3.1 최초 적용: 전체 과실288개와 줄기 물리를480Hz로 계산

과실9g, 줄기 힘/토크와 분리 조건, 오른팔 물리 설정을 연결하고 물리480Hz와 렌더60Hz를 분리했다. 외력은 매 물리tick 갱신한다. 분리 조건40ms는480Hz에서20tick=41.667ms로 충족된다.

물리 검증은0.1N 유지 시 미분리,3N 당김 시 실제 분리와 약0.90448m 하강, 최종287개 부착/1개 분리를 확인했다. 이는 줄기·중력 시험이며 정상 파지·운반·적재 성공 시험이 아니다.

초기 GUI 성능 비교(준비30/측정120프레임, 정책·센서·ROS 송신 없음):

| 초기 CPU PhysX 조건 | 물리 Hz | 측정 FPS | 물리 호출/프레임 |
|---|---:|---:|---:|
|288개 동적 과실+줄기+진단|480|8.30|100.63ms|
|같은 물리, 추가 상태 진단만 생략|480|8.27|102.67ms|
|과실288개 kinematic, 줄기 생략 대조|480|22.22|36.25ms|
|같은 고정 과실 대조|60|89.52|4.27ms|

현재 조건의 전체120.44ms 중 물리100.63ms(83.5%), 줄기7.06ms, 렌더9.90ms, 추가 검사2.38ms였다. 따라서 진단 로그만 줄여 해결할 문제가 아니었다. 당시 실제 설정은 CPU/NumPy·GPU dynamics=false·MBP였다. 과거 문서의 “GPU 검사”는 RTX가 있는 Isaac 실행을 뜻했으며 GPU PhysX 사용 증거가 아니었다.

마지막60Hz 대조는 카메라/과실 높이가 약8.05mm 달라 완전히 같은 초기 상태가 아니고,89.52FPS는 이전 Nav2 주행 실측값도 아니다.

### 3.2 대기60Hz/수확480Hz 전환과 작업 주변 과실만 활성화

전체288개를 항상 동적으로 계산하던 경로에서 작업 영역 중심으로 변경했다. 오른팔 장착점 반경0.8m, 유지 반경1.0m를 사용하고 여러 활동 영역은 합집합으로 처리한다. 멀리 있는 부착 과실은 고정하고 줄기 계산을 생략한다. 분리된 과실은 영역 밖에서도 동적 상태를 유지한다. 종료 후 안정 여부를 확인해60Hz로 복귀한다.

이는 적용한 최적화지만 멀리 있는 과실의 자연 흔들림을 생략하는 모델 단순화도 포함한다. 근처 비목표 과실은 이웃 충돌 때문에 활성화한다. 과실 위치·앵커·원래 자세를 재생성해 분리를 지우는 방법은 사용하지 않았다.

검증107개 및3개 sim 패키지 빌드 통과. 실제 자동 물리19항목, 전체288개 기준 물리15항목 통과. 실제 fleet6시뮬초에서60→480→60Hz,360렌더/1,200물리tick, 주변3개만 활성, 자연 분리0개를 확인했다.

동일0.08m/s 명령에서도 주기 전환 후 바퀴 odom 응답은 약0.0673→0.0793m/s 차이가 남았다. 고정60Hz 대비 전환 시험의 실시간 배율은0.725→0.483(약43.5→29.0갱신/벽시계초)이었다. 짧은 headless+센서 조건이며 이후 GUI 수확 FPS와 직접 개선율을 비교하면 안 된다.

### 3.4 성능을 논하기 전에 물리 조건과 화면 표시의 오류 수정

충돌 시각화 비교에서 농장 팔 convexHull과 전달 팔 convexDecomposition의 차이를 발견했다. 오른팔15개 메시와 여섯 몸체의 질량/COM/관성, 집게 카메라 합성, 자기충돌, 재질, drive, 관절·접촉 설정을 전달 환경에 맞췄다. GPU dynamics/GPU broadphase/TGS, 팔solver12/4를 적용했다. 실제115항목 대조와56개 검사는 통과했지만 수확 적재는0/1이었다.

이 조치 이후의 GPU 성능 수치를 이전 CPU 성능과 같은 실행 조건으로 취급하면 안 된다. 학습은 고정 베이스, 농장은 이동 차체와 별도 왼팔/바퀴 관절이라는 차이도 남는다.

별도로 엔진 내부 과실 pose가 움직이고 성공 로그까지 남는데 화면은 초기 위치에 있는 문제를 재현했다. 원인은 사용자 정의 matrix xform이었다. 고정/초기 배치를 표준 translate/orient/scale로 변경했다. 통제 이동·낙하23표본에서 물리/표시 오차0.550647m→0.000590m(root 오차0m)를 확인했다. 이 시험도 자연 파지 성공 시험은 아니다.

근거: [물리 정렬·표시 동기화](HARVEST_PHYSICS_INSPECTION_20261008.md), [로봇암팀 진단 회신](TEACHER_DIAGNOSTIC_REPLY_20261008.md).

### 3.5 480/240/120/60Hz 실제 수확 비교

학습 물리 정렬 후, 각각 새 프로세스·seed713·SEC10/Bed01/Pepper0017 yellow 첫 배치·정책20Hz·동일 표시 조건으로1회씩 비교했다. 이 표는 USD 쓰기 최적화 이전 결과다.

| 물리 Hz | 작업 평균 FPS | POLICY FPS | 적재 | 결과 |
|---|---:|---:|---:|---|
|480|4.28|4.31|0/1|복귀접촉2.804N, RETURN_FAILED, 실제정지 확인|
|240|7.33|7.68|0/1|복귀접촉3.294N 후 실제정지 미확인|
|120|13.95|12.42|0/1|복귀접촉4.072N 후 실제정지 미확인|
|60|22.45|19.67|0/1|이웃 과실 분리 후 실제정지 미확인|

60Hz POLICY는15프레임으로 짧다. 낮은 Hz에서 FPS가 증가했지만 수확 안정성을 확보한 것은 아니다. 네 프로세스의 종료0과 수확 실패를 구분한다.

초기 GPU `foundLostPairsCapacity` 부족(필요최대4,048,988/설정2,097,152)을 확인했다. 용량4,194,304로 늘려 위 네 조건을 다시 실행했고 같은 오류0건을 확인했다. 물성을 완화한 것이 아니라 장면 처리 버퍼 부족을 수정했다.

480Hz의 약232ms/프레임 중 물리 약196ms, 렌더/Kit 약20ms, 외력 약4ms, 접촉 약5ms였다. 추가 계측은 simulate 약0.34ms/fetch_results 약24ms였다. 이 시점에는 fetch 내부의 GPU 계산·복사·USD 쓰기를 분리하지 못했다.

### 3.6 USD 쓰기 횟수 축소 — 현재 유지

물리480Hz의 외력·step·접촉8회는 유지하고, USD 위치·속도 쓰기만 렌더 프레임의 마지막tick에 한다. 중간7회는 생략한다.60Hz에서는 기존 경로를 사용하고 예외 시 원래 설정을 복구한다. 독립 수확 UI에만 활성화했다.

| 같은 seed713의 당시 비교 | 작업 FPS | 물리/프레임 | 현재 채택 여부 |
|---|---:|---:|---|
|변경 전|4.28|195.84ms|기준|
|모든 로봇 물리 유지 + USD 쓰기 축소|4.67|171.66ms|유지|
|다른 두 로봇 정적화 + USD 쓰기 축소|7.01|102.43ms|철회|

현재 채택한 개선은 당시 약9% FPS 증가였다. 과실 PhysX/USD/Fabric root 오차0m, 하위 메시 최대1.3e-15m를 확인했다. 별도 상자 시험은480→60→480Hz·sleep·tensor 재활성8시뮬초/3,420tick, 최대오차1.92e-8m로 통과했다. 정적화 철회 후 스케줄러15/UI17/진입점2개 검사 통과.

### 3.7 다른 로봇 정적화 — 요구 위반으로 철회

예찰·선별 로봇43강체/42관절을 정적으로 만드는 시도를 했다. 하지만 사용자가 요구한 네 로봇 동시 운용에 맞지 않아 함수·호출·전용 검사를 제거하고 새 stage에서 동적 물리를 복원했다. 원본 USD에는 저장하지 않았다.

**7.01FPS 또는 물리 비용48% 감소는 현재 채택한 성과가 아니다.** 현재 장면97동적강체/3관절계를 유지한 수치만 후속 판단에 사용한다.

### 3.8 Nsight로 GPU 계산·복사·CPU 대기 분리

Nsight Systems2025.3.2로 CUDA/NVTX/OSRT와 PhysX 내부 profile zone을 기록했다. 대기60Hz76tick + 수확480Hz352tick=428tick. CPU IP sampling은 권한 제한으로 수행하지 않았고 시스템 보안 설정은 변경하지 않았다. Nsight 부하가 있으므로 FPS 비교는 별도 비계측 프로세스로 실행했다.

| 구간/지표 | 직접 계측값 |
|---|---:|
|USD 쓰기 없는 수확tick `fetch_results`|17.843ms/tick|
|같은 구간 CUDA 커널 실행 시간 합집합|15.924ms/tick|
|복사까지 포함한 GPU 실행 비중|fetch 구간89.7%|
|GPU→CPU 복사|전체428tick 평균0.0619ms/tick|
|simulate 호출|평균0.394ms/tick|

CUDA 커널515,266개가 모두 동일 Isaac 프로세스/GPU/context의 fetch 구간 안에 있었다. 렌더·Teacher CUDA 계산을 물리 비용에 포함한 결과가 아니다. 결론은 GPU→CPU 전송보다 GPU 관절계 솔버 실행이 주병목이라는 것이다. GPU 전체 포화 또는 커널 시간 전부가 순수 산술 연산이라고 단정하지 않는다.

상위 커널 `artiSolveInternalConstraintsTGS1T`, `artiPropagateRigidImpulsesAndSolveSelfConstraintsTGS1T`는 각각15,408회=428×36, launch1block×32thread였다. 공식 구현에서 thread 하나가 관절계 하나를 처리하므로 현재처럼 관절계가 적을 때 이 커널은 큰 GPU의 병렬성을 충분히 활용하기 어렵다.

GPU는 활성 강체·관절계의 solver 반복 횟수를 각각 최대값으로 합친다. 농장 수확팔12/4와 예찰/선별32/1이 함께 있어 실제32/4였다. 기존115항목 속성 일치만으로 전체 장면 실행까지 같다고 할 수 없음을 추가 정정했다.

전달 학습 과실도 기본16/1이고 해당 설정에서 덮어쓰지 않으므로 학습 전역은 소스상16/4로 예상된다. 학습팔12/4를 곧 전역12/4로 표현하면 안 된다. 학습 전역의 실제 kernel 추적은 미실행이다. 다른 로봇 반복 횟수나 전역 상한은 이번에 임의 변경하지 않았다.

공식 구현: [최대값 취합](https://github.com/NVIDIA-Omniverse/PhysX/blob/107.3-physx-5.6.1/physx/source/gpusolver/src/PxgContext.cpp#L974), [TGS 반복](https://github.com/NVIDIA-Omniverse/PhysX/blob/107.3-physx-5.6.1/physx/source/gpusolver/src/PxgTGSCudaSolverCore.cpp#L1327), [관절계별 thread](https://github.com/NVIDIA-Omniverse/PhysX/blob/107.3-physx-5.6.1/physx/source/gpuarticulation/src/CUDA/internalConstraints2.cu#L1554).

## 5. 미해결 사항과 보고서 결론의 범위

- 현재 농장 수확 성공 문제는 남는다. 각1회 성능 비교로 농장 전체 성공률을 주장하지 않는다.
- 최종 네 로봇 동시 미션, Nav2와 수확 동시 운용의 장시간 성능, 실물은 검증하지 않았다.
- CPU와 학습GPU의 수치·접촉 차이, 실제 학습 전체 장면 solver 반복의 대조가 필요하다.
- 낮은 Hz에서 안전 정지 미확인 사례가 있어 단순FPS 증가만으로 낮은 Hz를 채택할 수 없다.
- 다른 로봇 정적화 성과와 내부 로그만으로 시각적 운반을 확인했다고 한 해석은 철회했다.
- 첫 계측의 optional SDK API 오류·초기 buffer 부족·시작 중 native 종료 등 실패 기록은 최종 정상 시험과 분리 보존했다.

보고서의 결론은 “최적화 완료”가 아니라 “실행 구조 개선과 정확성 오류 수정 후, 실제 GPU 솔버 병목을 분리했고 CPU 비교의 개선 여지를 확인했으며 최종 물리 조건 선택을 위한 회귀 검증이 남는다”가 적절하다.
