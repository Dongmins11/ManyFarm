## 1. 준비와 빌드

Isaac용 Python과 비전용 robot_venv Python은 별도 환경이다. 아래 Isaac 경로는 이전 사용자 환경에서 확인된 경로를 사용한다. 실제 PC에서 실행 파일의 존재를 확인하고 다르면 실제 경로를 지정한다.

비전 의존성이 설치된 **robot_venv를 활성화한 터미널**에서:

```bash
cd ~/main/farm_project
source /opt/ros/jazzy/setup.bash
: "${VIRTUAL_ENV:?먼저 비전용 robot_venv를 활성화하세요}"
export FARM_ISAAC_PYTHON="$HOME/isaac/env_isaaclab/bin/python3.11"
export FARM_VISION_PYTHON="$VIRTUAL_ENV/bin/python"
test -x "$FARM_ISAAC_PYTHON"
test -x "$FARM_VISION_PYTHON"
```

두 `test`가 성공하는지 확인한다. Python 심볼릭 링크를 임의로 시스템 Python 경로로 바꾸지 않는다. 소스/인터페이스를 새로 반영했거나 아직 빌드하지 않았다면:

```bash
bash scripts/build.sh sim
source scripts/env.sh sim
python robot/ros_ws/src/farm_interfaces/examples/verify_interfaces.py
```

공통 workspace 빌드 후 sim workspace를 빌드하는 구조다. 인수인계 문서 ZIP만 적용했다면 재빌드는 필요 없다. 최신 통신 코드를 받은 관제·로봇 터미널은 새 install을 source하고 노드를 재시작해야 한다.

새 clone에서 USD가 `version https://git-lfs.github.com/spec/v1`로 시작하는 짧은 텍스트라면 Git LFS 객체를 받지 못한 상태다. Git LFS가 설치되고 해당 저장소 접근이 되는 환경에서 `git lfs pull`을 실행한다. USD가 참조하는 자산과 모델 파일도 로컬에 있어야 한다.

ROS_DOMAIN_ID는 과거 기록의 13/15/77 중 하나를 임의로 고정하지 않는다. 참여 터미널·실물 장비의 현재 설정과 통신 범위를 맞춘다. `scripts/env.sh`는 workspace를 source하는 스크립트이며 Domain ID를 설정하지 않는다.

## 2. 한 번에 예찰·수확 실행

```bash
cd ~/main/farm_project
source scripts/env.sh sim
ros2 launch farm_sim_runtime all.launch.py \
  project_root:="$PWD" \
  isaac_python:="$FARM_ISAAC_PYTHON" \
  vision_python:="$FARM_VISION_PYTHON" \
  harvest:=true device:=0
```

**`harvest:=true`가 필요하다. 기본값은 false다.** Isaac 하나, 예찰 bringup, 수확 bringup, 수확 평가 노드, RViz가 조합된다. 수확이 켜지면 기본 예찰 프로파일은 `scout_fleet_runtime.yaml`로 선택되어 다중 로봇의 clock/장치 설정을 사용한다.

- 예찰만 실행: `harvest:=false`.
- 수확 서버만 시험: `harvest:=true scout:=false`. Isaac 내부의 두 로봇 자산은 유지될 수 있다.
- 화면 모니터링 제외: `rviz:=false`.
- headless Isaac: `headless:=true`.
- 로봇 서버 기동은 Goal 전송과 다르다. 관제 또는 아래 시험 클라이언트가 작업을 요청해야 한다.

`farm_bringup all.launch.py`는 이 명령의 대체가 아니다. 전체 실행과 아래 개별 실행을 중복 기동하지 않는다.

## 3. 터미널별 분리 실행

각 터미널에서 프로젝트 루트, ROS 환경, `source scripts/env.sh sim`을 준비한다. Isaac 터미널에는 FARM_ISAAC_PYTHON, 예찰 터미널에는 FARM_VISION_PYTHON을 지정한다.

ros2 launch farm_sim_runtime isaac.launch.py \

  fleet_config:=sim/ros_ws/src/farm_sim_config/config/harvest_fleet.json

## 4. 현행 메시지로 시험 요청

먼저 인터페이스와 서버 확인:

```bash
ros2 interface show farm_interfaces/action/ScoutArea
ros2 interface show farm_interfaces/action/HarvestTask
ros2 action list -t
```

예찰 Section 두 개를 순차 요청:

```bash
python control/scripts/send_scout_area.py --section SEC01 SEC02
```

현재 인자는 `--section`이며 한 번에 여러 이름을 적으면 내부에서 단일 Section Goal을 순차 전송한다. 첫 실패/취소 시 다음 Section 전송을 중단한다. 과거의 `run_bed_scout_harvest.py --sections ...`를 현행 실행 진입점으로 안내하지 않는다.

수확 이동만 확인하는 시험 Goal:

```bash
ros2 action send_goal /harvest_01/harvest_task farm_interfaces/action/HarvestTask \
  "$(python sim/tools/harvest_smoke_goal.py --section SEC01 --fraction 0.313 --expected-count 0)" \
  --feedback
```

이 Goal은 설정 경로에서 만든 이동 시험 입력이다. 실제 예찰 Result의 Task가 아니므로 expected-count 0과 audit 실제 개수의 차이를 예찰 성능 지표로 해석하지 않는다. 실제 연동에서는 성공한 ScoutArea Result의 Task를 그대로 사용한다. 성공한 task_id를 재사용하지 않는다.

정상 이동 시험의 기대 결과는 `result_code=SUCCESS`, `error_code=NONE`, `harvested_count=0`, `failed_count=0`이다. 박스 안에 과실이 있어도 실제 수확량으로 보고하지 않는다.

## 5. 결과와 로그

| 내용 | 현재 경로·위치 |
|---|---|
| 예찰 결과 | `sim/runs/scout_survey/<세션>/survey.json` |
| 예찰 비전 worker | `sim/runs/scout_survey/vision_<ID>/vision_worker.log`; 실제 경로는 survey.json의 `vision_worker_log` 확인 |
| 독립 비전 출력 | `sim/runs/scout_vision/` |
| 수확 박스 평가 | `sim/runs/harvest_motion/<평가세션>/<task_id>_<event_id>.json` |
| Isaac 정답 snapshot | `sim/runs/runtime/harvest_scene.json` |
| 구동 진단 | `sim/runs/drive_diagnostics/` (진단 기능이 동작하는 실행) |
| 임시 예찰 클라이언트 | `runs/control/SCOUT_<ID>.jsonl` — 현행 코드의 기존 경로 |
| ROS launch 로그 | launch가 출력하는 로그 폴더; 일반적으로 `~/.ros/log/` |

새 시뮬 전용 로그는 sim 안에 둔다. 기존 임시 클라이언트의 `runs/control/`를 문서상으로만 sim 경로로 바꾸거나 실제 파일을 승인 없이 이동하지 않는다.

가장 최근 수확 평가 파일의 핵심 값 확인:

```bash
python - <<'PY'
import json
from pathlib import Path
paths = list(Path('sim/runs/harvest_motion').glob('*/*.json'))
if not paths:
    raise SystemExit('수확 평가 파일이 없습니다. 평가 노드와 작업 종료 이벤트를 확인하세요.')
path = max(paths, key=lambda p: p.stat().st_mtime)
record = json.loads(path.read_text())
print(path)
print(json.dumps({
    'task_id': record.get('task_id'),
    'result': record.get('result'),
    'evaluation': record.get('evaluation'),
}, ensure_ascii=False, indent=2))
PY
```

- `OK`: 정상 비교; `actual_in_workspace`, `expected_count`, `count_delta`, `repeated_gt_ids` 확인.
- `SKIPPED_NOT_ARRIVED`: 이동 성공이 아니어서 평가 생략.
- `UNAVAILABLE`: snapshot 누락·시간 차이 등으로 평가 불가. `error` 확인.

## 7. 임시 시뮬 관제로 한 사이클 실행 — 2026-10-07

위 all.launch.py를 켠 뒤 별도 터미널에서 실행한다. 재빌드는 필요 없다.

```bash
cd ~/main/farm_project
source /opt/ros/jazzy/setup.bash
source scripts/env.sh sim
/usr/bin/python3 sim/tools/temporary_control.py
```

`Section>`에 `SEC01` 등 설정의 Section을 입력한다. 예찰 성공 Result의 원본
harvest_tasks를 순서대로 수확 Action에 보내고 각각의 종료를 기다린다.
관제와 launch의 ROS_DOMAIN_ID는 같아야 한다. 외부 관제와 동시에 작업을 보내지 않는다.
한 사이클만 실행하려면 `--section SEC01`을 붙인다. `q`는 대기 중 종료,
Ctrl+C는 자기 작업 취소와 종료 결과를 기다린 뒤 프로그램 종료다.

예찰 실패/취소의 부분 목록은 전송하지 않는다. 수확 작업 FAILED/CANCELED는 남은 큐를
중단한다. 수확 SUCCESS에서 개별 과실 실패 수량이 있더라도 다음 작업으로 진행한다.
정지 확인 실패 시 새 작업은 차단한다. 성공 여부와 실제 적재 수량은 구분해서 출력한다.
로그는 `sim/runs/temporary_control/*.jsonl`에 Goal/Feedback/ROS 종료 상태/Result를 저장한다.
기존 control/scripts/send_scout_area.py는 여전히 예찰만 요청하는 도구다.

임시 도구는 로봇 FSM/좌표/작업 ID를 수정하지 않는다. 예찰 Window와 Teacher 근거리
후보 범위 차이 및 적재 성공률 문제를 해결하는 도구는 아니다. 직접 확인한 것은
메시지/순차 전송 단위검사와 CLI 로딩이며, 실제 Isaac/Nav2 전체 사이클은 미검증이다.
삭제할 때는 `sim/tools/temporary_control.py`, `sim/tests/test_temporary_control.py`와
이 안내를 제거하면 된다. 운영 launch에는 자동 등록하지 않았다.

## 바구니 평행 3빔 통과 계수 — 2026-10-19

기본 `student_d435`는 좌표상 안착 대신 바구니 입구의 평행 3빔 통과로 수량을 센다. 기존 중앙 상하 2빔 배치는 D-043으로 대체했다. 190×190mm 내측 입구의 한 벽에서 47.5/95/142.5mm, 입구보다 5mm 아래에 세 빔을 둔다. 송신기 3개와 수신기 3개이며 각각 반대 벽을 바라본다.

`farm_sim_config/config/student_policy.json`의 `basket_lasers`가 배치/시간 설정이다. 헤드 외형은 임시 12×6×12mm, 내측 벽에 밀착한다. 광축 끝점은 벽에서 7mm 안쪽(헤드 앞면보다 1mm 앞)이라 벽/자기 센서를 감지하지 않는다. 실물 제품의 확정 치수나 질량을 의미하지 않는다.

운영 URDF `sim/assets/robots/harvest_robot/urdf/harvest_robot.urdf`에 고정 헤드/optical 링크를 저장했다. 두 운영 USD 계열의 `configuration/harvest_robot_base.usd`에 같은 장착부를 저장하여 기본·flat·tire USD 참조에도 적용한다. 장착 경로는 `<robot>/base_link/BasketLasers`, 빔은 `beam_1..3`, 광축은 `basket_laser_<1..3>_<emitter|receiver>/optical`이다. 초록은 비차단, 빨강은 차단이다. USD의 헤드 위치에서 PhysX raycast를 실행하며 로봇 pose를 따른다. 학습/전달본의 해시 검증 URDF·USD는 보존한다.

실제 배출 허가 이후 전부 비차단 50ms로 준비하고, 어느 빔이든 차단된 뒤 전부 비차단이 50ms 유지되면 1개를 집계한다. 동시에 여러 빔을 가려도 한 개이며 재차단/튀어오름은 같은 시도에서 추가 집계하지 않는다. 2초 동안 막힘, 초기부터 차단, 취소 후 입력은 성공을 만들지 않는다. 다음 과실의 배출 시도에서 다시 준비한다.

`BASKET_LASER_ARMED`, `BASKET_LASER`, `ATTEMPT_RESULT` 로그를 확인한다. `success_source=basket_parallel_lasers`, `beams_seen=[1..3]`, `identity_confirmed=false`, `direction_confirmed=false`를 기록한다. `success_count` 증가는 기존 내부/상위 `feedback.success_count`, 최종 `result.harvested_count` 및 `arm_feedback` 적재 누적에 전달된다. 전체 Action 성공에는 별도로 팔 접힘·안전정지 확인이 필요하다. 취소/후속 실패에도 이미 확인한 통과 수량은 보존한다.

센서는 이름/색/목표 ID로 필터하지 않는다. 통과 방향·파프리카 식별·최종 잔류는 확인하지 못하며 이물체도 집계될 수 있다. 일반 Teacher 비교 경로는 기존 안착 판정을 유지한다. 실제 GPIO/PLC 센서 입력은 아직 연결하지 않았다.

배치 설정을 바꾸면 Isaac Python/pxr 환경에서 `python sim/tools/build_basket_laser_assets.py`로 URDF·USD를 함께 갱신한다. 물리 검증은 `python sim/tools/check_basket_laser.py`이며 실제 과실 충돌체와 익명 큐브를 낙하시킨다. 소스/설정은 `farm_sim_devices`, `farm_sim_config` 두 패키지를 빌드하고 Isaac과 시뮬 장치를 정상 재시작하면 적용된다. 사용자 실행 프로세스는 이 작업에서 재시작하지 않았다. 검증 조건과 남은 초기 영상 지연 제한은 PROJECT_STATE §73 및 `sim/runs/basket_parallel_lasers_20261019/verification.json`을 따른다.
