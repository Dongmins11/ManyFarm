# 배출 Action 연결 4단계 설계 — 2026-10-18

## 확정 사항과 구현 상태

사용자는 Jetson이 적재함 열기·배출·닫기를 한 번의 Action 요청으로 수행하는 방식을 확정하고 연결 설계를 요청했다. Jetson 모터 코드는 팀원이 담당하며 Pinky는 요청·상태 전달·인계 흐름을 담당한다. 팔은 관제와 직접 통신하지 않는다.

기준은 작업 브랜치8466ac1 + 사용자 PC에 적용한1~3단계 미커밋 변경이다. 사용자 제공 로그로3단계62개 테스트 통과와 git diff --check 통과를 확인했다. 로봇 배포/ROS 빌드/실제 장치 검증은 미실행이다.

이 변경은 설계 문서만 추가한다. 아직 배출 Action 클라이언트나 새 ROS 형식을 구현하지 않았고 기존3단계 실행 코드도 바꾸지 않았다. 실제 이름·메시지·물리 완료 판정 방법은 미확정이다.

## 확정한 정상 순서

1. 현재 좌표 전체 수확이 끝난 후 관제의 DockTransfer를 수락한다. 실행 중 수확을 중간 선점하지 않는다.
2. 기존 준비 확인과 제자리 왼쪽90도 회전·정지를 완료한 후 DOCK_READY를 보고한다.
3. 관제에서 전달된 DOCK_STABLE을 확인한다.
4. Pinky가 Jetson에 배출 Action을 한 번 요청한다. Jetson이 열기→배출→닫기를 수행한다.
5. 열기만 완료한 Feedback이나 명령 접수 응답은 배출 완료가 아니다. 전체 배출·닫힘 완료를 의미하는 성공 Result를 확인한 뒤 TRANSFER_COMPLETE를 관제에 보고한다.
6. TRANSPORT_CLEAR를 기다린다. 그 전에 회전하거나 주행하지 않는다.
7. 같은 인계의 닫힘 포함 배출 완료 증거를 확인하고 제자리 오른쪽90도 복원을 수행한다. 닫기 Action을 다시 요청하지 않는다.
8. 기존 복원·정지 검증을 통과하면 인계 Action을 완료하고 성공량 초기화 조건을 충족한다.

1단계 구현의 적재량 초기화 시점은 배출 완료만이 아니라 인계/복원까지 정상 완료된 시점이다. 배출 후 복원 실패 시 보관된 수량은 실제 잔량 측정값이 아니라 복구 전 논리 기록일 수 있다. 이 시점을 임의로 변경하지 않는다.

## 복원 단계의 중복 닫기 방지

3단계의 restore_devices는 아직 외부 장치 복원을 요청하는 확장 지점이다. 기존 서비스 방식 전체의 의미를 바꾸지 않는다. 새 배출 Action 어댑터를 선택했을 때만 해당 요청을 '현재 인계의 배출·닫힘 완료 결과 확인'에 연결한다.

닫힘 증거가 없거나 이전 인계의 결과이면 복원 회전을 허용하지 않는다. 실패·취소 Result나 open 완료 Feedback으로 닫힘을 추정하지 않는다. 캐시는 새 인계 시작/실패 시 무효화하며 프로세스 재시작 시 자동 안전 확인에 사용하지 않는다. 기존 복구 저널 차단을 유지한다.

별도 팔 자세 변경은 사용자와 합의되지 않았다. 정상 수확 시작/완료 시 접힌다는 기존 전제를 유지하며 새로운 접힘 명령이나 자세를 만들어 넣지 않는다. 현재 prepare_arm 서비스가 미설정이라는 사실을 자동 성공으로 바꾸지 않는다. 팔/박스 담당자와 준비 확인의 실제 연결을 정해야 한다.

## 실패·취소 경계

- Goal 거절, 서버 미연결, 결과 실패, 시간초과, 연결 손실은 전체 완료가 아니다. TRANSFER_COMPLETE를 보내지 않고 자동 재요청/복원 회전을 하지 않는다.
- 취소 ACK는 종료 Result나 모터 정지 확인을 대신하지 않는다. 취소 이후 Jetson이 닫는지/중간 정지하는지 아직 미정이므로 임의로 가정하지 않는다.
- 물리 정지와 닫힘/배출 완료는 서로 다른 사실이다. 취소 후 정지 확인이 되어도 정상 인계 완료로 처리하지 않는다.
- 열기/닫기 시간이 지났다는 이유만으로 배출·닫힘 성공을 생성하지 않는다.

## 팀과 확정할 통신 항목

1. Action의 패키지·타입·endpoint와 Goal/Feedback/Result 필드.
2. 현재 인계와 요청/결과를 연결할 식별 방식 및 중복 요청 처리.
3. 배출·닫힘 완료를 Jetson이 어떻게 확인하고 어떤 Result로 보장할지. 수확물 유출/걸림/닫힘 실패를 포함하되 센서나 알고리즘을 임의 선정하지 않는다.
4. 취소/통신 끊김/재시작 시 장치 정지 및 복구 확인 방식.

## 현재 Result 계약 — 복수 오류 배열 (D-046, 2026-10-18)

이 절이 앞 절의 discharge_complete/단일 error_code 및 error_free 설명을 대체한다. 사용자 승인: 배출 미완료를 DISCHARGE_FAILED로 보고하고 복수 오류를 함께 전달하므로 별도 완료 bool 제거.

| 필드 | 자료형 | 의미 |
|---|---|---|
| transfer_id | string | Goal에서 받은 인계 식별값 |
| error_codes | string[] | 발생한 오류 전체. 정상은 빈 배열 [] |
| error_message | string | 상세 설명 |

오류 구분: OPEN_FAILED, DISCHARGE_FAILED, CLOSE_FAILED, INTERNAL_ERROR. 배출과 닫기 모두 실패하면 두 코드를 함께 반환한다. NONE 원소는 사용하지 않는다. 알 수 없는 오류라도 배열이 비어 있지 않으면 실패로 판정한다.

전체 성공은 현재 transfer_id 일치, Action 성공, 빈 오류 배열을 모두 만족해야 한다. 오류 코드가 없다는 이유만으로 취소/실패/미수신 결과에서 배출 또는 닫힘을 추정하지 않는다. 감지 방식은 Jetson 책임으로 보류한다.

공통 판정의 finish(reply, action_succeeded=...)에서 기존 error_free 인자를 제거했다. error_codes를 직접 검사하며 빈 문자열/None/객체를 빈 배열로 간주하지 않는다. 성공 여부를 오류 배열과 별도 bool로 중복 전달하지 않는다.

직접 검증: test_discharge_result.py 15개 PASS. 복수 오류 보존과 배출/닫기 동시 실패 시 완료·역회전 차단을 추가했다. 기존 공통 미션/회전을 그대로 호출하는 모의 시험이며 실제 ROS 통신은 아니다. 기존25개 시험 결과와 이번15개 결과를 합산해서 새 전체 시험 수로 표시하지 않는다.

변경 파일은 공통 판정 모듈, 해당 시험 및 문서4개. 현재 운영 런치에는 연결하지 않았다. ROS Action 형식 파일/클라이언트/운영 어댑터 구현, 취소·정지 계약은 후속 작업이다. 직전 mock 패치 적용 후 이번 errors 패치를 적용하고 verify_stage4_errors.bash로 재현한다. 되돌림은 이번 패치만 git apply -R --check 후 역적용한다.
